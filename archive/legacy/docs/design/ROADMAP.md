# 从 C5 到完整目标的完成路线

日期：2026-09-23。状态：实施提案；阶段验收通过后再记录为已完成。

本路线以 [C5 可执行示例](effect-sample/README.md) 为起点，按个人或小团队、单机单进程优先安排。目标是让同一份类型化业务声明贯通执行、资源管理、事件恢复、模块观察、场景替换、压力测试与配置启动。发布代码和旧试验版提供复用参考，其已有能力需要在新接口下重新验证。

路线以可运行的场景和明确的失败行为衡量进度。阶段名称表示下一步要证明什么；不以文件数量、抽象数量或主观完成百分比衡量进度。工期在早期探针验证后，依据实际完成速度估算。

## 1. 完成的含义

保留当前用户侧的核心结构：在 Effect instance 中声明契约并实现 impl，Handler 提供原子操作，impl 解释请求并组合调用。库按分类生成注册，Scope 额外声明生命周期。控制、参数、能力、资源分别有明确表达，库负责将它们接入执行。只有具体场景暴露问题时，才调整这些边界。

最终应交付三个可独立使用的里程碑：

| 里程碑 | 包含阶段 | 用户实际得到什么 |
|---|---|---|
| A：可用的同步语言内核 | 0—2 | 声明多个操作、选择分支、组合业务参数，可靠使用与释放资源，定位失败 |
| B：完整的进程内执行模型 | 3—4 | 等待与恢复、监听轮次、并发共享、取消和显式重试共同遵守同一生命周期 |
| C：可交付的框架 | 5—7 | 按模块观察、选择真实或测试实现、运行负载、从配置装配，并有包、文档及应用证据 |

首个完整版本的边界是进程内执行。分布式调度、进程重启后的执行恢复、任意宿主函数序列化、动态编译插件和图形化 IDE 留待独立需求。配置加载选择已编译能力；配置本身不保存活资源、线程或任意闭包。

## 2. 当前起点

当前 C5 已通过 16 项运行检查与 21 项编译失败检查，覆盖自动注册、instance 内的 impl、句柄解析、同名方法选择、祖先资源投影及原有业务行为。当前验证限于 Effect 层，AST 与 interpreter 的实现继续单独设计。这是本轮基线记录，后续修改后应重新验证相关部分。

| 已有基础 | 仍需验证的边界 |
|---|---|
| Effect / Handler / Signature / impl 的类型连接 | 异构节点和控制分支中的连接 |
| Input 与祖先方法约束传播，Ready 保存本次资源 | 多来源参数、跨分支共享、多个 scope 能力 |
| compile 生成可重复调用的闭包 | 挂起后的执行身份和恢复位置 |
| 统一 Result、类型化失败的跨链传播 | 取消、次生失败和恢复策略的统一解释 |
| 同步 scope 的正常、失败、取消清理 | 静态 once、借用逃逸、等待与并发使用期间的清理 |
| Trace / Sink 注入和外围 middleware 样例 | 可关联的模块事件、快照、场景替换和负载执行 |

当前 Pending 是结果快照；Result 不持有可唤醒任务。Exports 支持字典推导；资源权限另由资源接口表达。impl 中的额外 IO 目前仍受书写约定约束。保留这些区分，避免将目标保证当成现有保证。

## 3. 阶段安排

### 阶段 0：固定基线，验证最可能返工的接口

**交付物**：一页当前语义约定，以及三个可编译的小探针。延续 C5 文件示例，不先重组整个仓库。

- 语义约定写清 Input、Require、Handle、Value、Failure、Ready、Result 的职责；区分成功无值、Pending 快照、业务失败、宿主异常与取消。逐条标记类型保证、运行保证和书写约定。
- 异构探针：将两种不同 Effect 放进同一控制容器，保留其参数检查、方法字典和结果类型关系；用一个错误连接验证拒绝路径。
- 资源探针：用一个带关闭计数的资源验证线性关闭责任如何穿过 impl、闭包及封装边界；同时试验借用不能逃出作用域的接口。具体机制由编译结果决定。
- 场景探针：同一业务结构分别接真实与内存能力，资源获取和释放使用配套实现。实例仍在编译时提供，启动时选择已编译的适配器或执行封装。

**通过条件**：探针有成功例和有意义的负例；若现有接口不能支持其中一个目标，在这里修改最小边界并复查 C5 写法。

**同时确定**：可配置的节点、参数转换和实现需要具名引用及解码契约；普通 Haskell 闭包仍可用于源码编排。先明确可导出的子集，后面再实现加载器。

**暂缓**：Free/Fix 的普遍改写、完整调度器、通用插件系统。递归表示按后续控制场景的需要选择。

### 阶段 1：跑通最小控制语言与参数连接

**交付物**：Node、顺序、Choose 三种控制结构；命名模块；参数汇合；最小执行事件。AST 外围组织控制，节点继续使用已经验证的操作执行机制。

- 区分注册身份、节点位置、执行实例和 scope 身份。两个节点引用同一注册，默认仍是两次调用；共享通过对同一次执行的显式引用表达。
- 为值来源建立带类型的引用，使两个来源可以汇成一份 Require；保持 Input 的能力关系与业务值关系独立。
- 用内存事件收集器记录开始、成功、失败、资源获取和释放。事件关联执行身份，观察读取这些记录。
- 控制层复用同一次上游资源，避免每个节点各自沿 Input 重开同一 scope。

**验收场景**：文件内容与一次调用提供的格式选项汇成报告参数；Choose 选择真实的一个分支。未选分支的计数始终为零；两个消费者引用同次读取时只读一次；显式发起两次读取时确实运行两次；参数类型错误被拒绝。

**通过条件**：有一个含不同 Effect 的完整控制程序，事件能说明哪些节点运行、为什么复用、失败来自哪里。样例作者仍能从注册看懂契约、从 impl 看懂行为。

**暂缓**：Parallel、事件监听、流式参数、图形化展示。

### 阶段 2：建立可依赖的资源与错误协议

**交付物**：阶段 0 资源探针的正式接口，嵌套 scope、有限的多 scope 需求、关闭责任、错误传播规则。

- once 表达静态关闭责任；借用有效期另有明确约束。普通结果、异构封装和闭包携带的引用必须遵守该约束。
- 从一个同时需要输入资源和输出资源的操作出发实现 layer；先支持具体的有限组合。
- 写清获取中途失败、嵌套关闭顺序、业务失败、清理失败及错误报告失败的处理顺序。
- 推荐起始规则：成功后的清理失败成为最终失败；主操作已有失败时保留主失败，次生失败进入可查询诊断。明确一次关闭责任的消费不等于底层外部关闭必然成功。

**验收场景**：打开两个资源，分别在第二个获取、业务执行、错误报告和关闭时注入失败；外部取消仍经过清理。成功取得的资源各自消费一次关闭责任，未取得的资源不被关闭；每个错误都有来源。

**编译负例**：重复消费关闭责任、错误 owner、借用越出有效期。运行时补充中断边界检查，区分编译器证明与运行测试覆盖。

**通过条件**：里程碑 A 成立。用第二个小领域的内存能力验证同一接口，例如会话查询与报告输出；只为发现的结构差异调整抽象。

**暂缓**：在使用者未停止时强行宣布 scope 已关闭、自动选择重试策略、任意资源插件体系。

### 阶段 3：实现单次等待、恢复和监听轮次

**交付物**：进程内任务身份、等待记录、恢复入口、取消入口和最小 Hanging；先使用可控事件队列逐步推进执行。

- Result 继续承担结果或状态视图；等待原因、恢复位置和任务身份保存在执行协议中。Pending 本身不自动成为可恢复任务。
- 推荐首版规则：显式挂起保留所属 scope；继续等待、恢复、完成、失败和取消各有明确转换。取消等待时使恢复入口失效，再完成资源退出。
- 恢复原执行沿用原执行身份；Loop 的新轮次创建新身份。事件重复投递最多恢复同一次等待一次。
- 首版 Loop 顺序执行各轮次，规定队列容量及满队列行为。外部事件通过同一调度入口进入。

**验收场景**：成功等待后恢复；等待中取消；取消后收到迟到事件；相同事件重复投递；恢复操作失败；两次独立监听轮次。事件由测试主动投递，检查不依赖猜测 sleep 时长。

**通过条件**：挂起不会误关仍需使用的资源；取消后不再运行旧回调；任务有明确终态，取消不能表现成可继续唤醒的等待。公开状态如何表示取消在本阶段定稿。

**暂缓**：进程重启恢复、跨机器消息、动态 hook 编辑和流式背压。

### 阶段 4：组合并发、共享、取消与显式重试

**交付物**：有父子归属的并发任务、共享调用的原子启动、取消传播、显式恢复与有界重试策略。

- 推荐首版 Parallel 规则：一个子任务失败，取消其余子任务，等待它们退出，再释放父 scope；完整保留触发失败与清理诊断。
- 共享以同一执行实例为单位，多个消费者只触发一次启动。注册类型、请求相同本身不构成共享理由。
- 重试创建新的尝试身份，次数及适用错误由用户显式指定；每次尝试的局部 scope 重新获取。外层 scope 的复用必须在结构中可见。
- 终态只能提交一次；取消与完成的竞争按已定义的状态转换处理。明确用户选择的恢复操作失败后如何传播。
- 区分等待外部事件与内部依赖循环；后者给出可定位的依赖路径。无法退出的使用者需呈现为未完成清理。

**主验收场景**：两个分支共享一个 scope，一个分支等待事件，另一个失败；取消等待，随后投递迟到事件。检查无旧回调执行、无重复关闭、无关闭后使用、无终态再次恢复，并能查到失败及取消来源。

**补充检查**：用屏障控制启动、完成、取消、释放的关键顺序；重复竞争测试辅助发现问题。重试到成功、次数耗尽、重试间取消均有预期事件序列。测试覆盖与状态规则共同作为证据。

**通过条件**：里程碑 B 成立。静态资源接口能够穿过实际并发与回调边界，阶段 2 的保证继续成立。

**暂缓**：任意调度策略、复杂重试 DSL、广泛性能调优。

### 阶段 5：将执行证据做成观察与测试工具

**交付物**：静态描述、运行快照、事件流三种视图；listen、log/show、场景 mock、最小 stress 入口。

- 扩展已有事件，按模块、注册、执行和 scope 关联；展示等待原因、失败来源、实际实现、耗时和资源状态。
- 阶段 0 的真实/内存适配扩展为正式场景选择，支持需要的 Handler 与 impl 绑定；获取和释放始终配套。
- stress 提供有限并发度、次数和输入集合，复用正常的启动、取消与清理协议。
- 明确观察覆盖框架操作边界；宿主函数内部的细节由主动事件补充。观察者失败的隔离规则与显式业务 Sink 的失败语义分别记录。

**验收场景**：同一业务描述依次使用真实后端、成功 mock、失败 mock 运行，事件指出采用的实现。开启观察不增加业务调用；观察者故障不会破坏框架清理；负载结束后无遗留任务、挂载或资源责任。

**暂缓**：图形化调试器、全量宿主函数追踪、专用遥测存储。

### 阶段 6：从配置装配同一套程序

**交付物**：稳定注册/实现标识、参数与值连接的契约、版本规则、配置导出与加载、已编译能力目录。

- 先在一个可执行文件中维护已编译能力目录，再按需求扩展分发。外部配置选择具名节点、转换和实现。
- 在运行外部业务操作之前完成结构、引用、类型契约和参数解码检查，构造带类型证据的执行封装。
- 对源码支持但暂不可导出的匿名表达式给出明确诊断；配置只接受阶段 0 定义并在本阶段细化的可导出子集。
- 明确配置版本、能力版本不匹配的诊断规则，不隐式猜测迁移。

**验收场景**：同一具名流程从源码与配置启动，业务结果及关键事件等价；错误参数、类型连接、缺失实现、依赖循环和版本不匹配在启动前被拒绝。活资源和运行闭包不进入配置。

**暂缓**：运行时编译任意 Haskell、热更新活动任务、任意执行快照持久化。

### 阶段 7：应用验证、整理公开接口并交付

**交付物**：可安装的包、稳定的公开接口、两份完整应用示例、错误诊断说明、扩展方式和版本迁移说明。

- 应用一沿用文件处理与报告；应用二验证不同结构，例如监听事件后查询会话并生成报告。先使用可控内存后端，必要处再接真实 IO。
- 比较重复声明、深层 inputOf、能力传递和测试布置的实际成本；按真实使用证据合并或移除抽象。
- 性能只测明确关心的路径：单次调用、共享、事件恢复和有限并发。区分框架开销与原子 IO 成本。
- 从 sample 提取已稳定实现；旧试验代码按模块评估复用，完成适用测试后再整合。更新专题文档中过时的接口与保证。
- 若之后涉及替换已发布框架 core，按既有独立维护与验证流程处理；此路线的功能验收不替代该流程。

**通过条件**：里程碑 C 成立。用户能从文档写出应用、理解错误、注入测试能力、观察执行、运行负载，并从配置启动受支持的流程；每项公开保证都有对应实现和证据。

## 4. 每轮工作的节奏

每轮只选择一个尚未证明的规则：先写一个具体使用场景及预期事件，再做最小实现，补充会真正区分对错的检查，最后复读 FileEffects 风格的用户代码并更新保证说明。新机制同时通过运行行为、适用的编译负例和用户侧可读性检查后，才作为下一阶段基础。

新增阶段时沿用已有事件与资源协议。发生接口返工时记录触发它的反例；不要为暂时没有使用者的通用性添加兼容层。

阶段 0、2、4、6 是主要回看点，分别回答：接口能否承载目标、资源保证是否成立、组合运行语义是否成立、配置能否恢复受类型检查的程序。未通过时缩小场景或修改局部机制，不跳过相应目标的验证。
